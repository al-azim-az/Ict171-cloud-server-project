## Project Overview

This project documents the complete manual setup of a multi-purpose Ubuntu server hosted on Microsoft Azure, accessible via the custom domain alazimazxyz.xyz with full HTTPS encryption.

Every component of the stack — from operating system provisioning to web server configuration, DNS management, SSL certificate installation, custom scripting, and automation — was implemented manually via SSH following Infrastructure-as-a-Service (IaaS) principles. No pre-built images or single-click installers were used.

### Server Components

- Custom HTML/CSS landing page at the root domain
- Live security audit dashboard at the status subdomain, generated by a custom Bash script
- Automated hourly refresh via cron
- Full HTTPS encryption across three subdomains using Let's Encrypt
- Defense-in-depth security: Azure NSG + UFW host firewall
- Comprehensive Markdown documentation on GitHub in English and Bangla

This is **defense in depth** — two independent firewalls (Azure NSG + UFW host firewall), so a misconfiguration in one does not expose the server.

## 1. Azure Virtual Machine Provisioning

The first step was to provision an Ubuntu Server VM on Microsoft Azure using the Azure Portal.

### VM Specifications

| Item | Detail |
|---|---|
| VM Name | ict171-server |
| Resource Group | ICT171-RG |
| Image | Ubuntu Server 24.04 LTS |
| Size | Standard_B2ats_v2 (2 vCPU, 1 GiB RAM) |
| Region | Australia East (Sydney) |
| Authentication | SSH public key (2048-bit RSA) |
| Admin Username | azureuser |

### Why Sydney Region?

The Australia East region (Sydney) was selected to minimise network latency for primary access from Perth. This decision was based on geographic proximity and Azure's lower data transfer costs within the Australian region.

### Network Security Group (NSG) Configuration

Three inbound ports were explicitly opened at the Azure NSG level:

- **Port 22 (SSH)** — administrative access via key authentication
- **Port 80 (HTTP)** — required for Let's Encrypt domain verification
- **Port 443 (HTTPS)** — encrypted web traffic

All other ports remain denied by default. This NSG is the first of two firewall layers, implementing defense-in-depth security principles.

## 2. SSH Configuration and Server Hardening

### Connecting to the Server

Initial connection was established from Windows PowerShell using the private key file:

```bash
cd C:\Users\alazi\Downloads
ssh -i ict171-server_key.pem azureuser@20.5.169.97
```

### Why SSH Key Authentication?

Password-based SSH authentication is vulnerable to brute-force attacks. SSH key authentication uses a 2048-bit RSA key pair where the private key never leaves the local machine. This approach is the industry standard for production servers and was selected to demonstrate security best practices.

### System Updates

```bash
sudo apt update && sudo apt upgrade -y
```

All packages were updated to the latest security patches immediately after provisioning, reducing exposure to known vulnerabilities.

### Host-Level Firewall (UFW)

In addition to the Azure NSG, a host-level firewall was configured using UFW (Uncomplicated Firewall):

```bash
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable
```

This two-layer firewall approach (cloud NSG + host UFW) is called **defense-in-depth** — even if one firewall is misconfigured, the other still protects the server.

## 3. Nginx Web Server Setup

### Installation

```bash
sudo apt install nginx -y
sudo systemctl enable --now nginx
sudo systemctl status nginx
```

Nginx was selected over Apache for several reasons: lower memory footprint (important on a 1GB RAM VM), better performance for static content, simpler configuration syntax, and superior handling of concurrent connections via its event-driven architecture.

### Custom Landing Page Deployment

A custom HTML/CSS landing page was developed locally and deployed to the server via the GitHub raw URL workflow:

```bash
sudo cp /var/www/html/index.nginx-debian.html /var/www/html/index.nginx-debian.html.bak
sudo curl -o /var/www/html/index.html \
  https://raw.githubusercontent.com/al-azim-az/ict171-cloud-server-project/main/index.html
sudo chown www-data:www-data /var/www/html/index.html
sudo systemctl reload nginx
```

### Nginx Server Blocks (Virtual Hosting)

Two separate Nginx server blocks were configured to serve different content on the same server based on the subdomain:

- `alazimazxyz.xyz` → Custom landing page (`/var/www/html/`)
- `status.alazimazxyz.xyz` → Security dashboard (`/var/www/status/`)

Nginx examines the `Host` header of each HTTP request to determine which subdomain is being accessed and routes to the appropriate content. This is the same virtual hosting technique used by major SaaS platforms like WordPress.com to serve millions of distinct sites from shared infrastructure.

## 4. DNS Configuration

### Domain Registration

The domain **alazimazxyz.xyz** was registered through Namecheap. The `.xyz` TLD was selected for its low cost and clean appearance for technology-focused projects.

### Switching to Namecheap BasicDNS

The domain initially used Custom DNS pointing to Namecheap's hosting nameservers. Since this project uses Azure for hosting (not Namecheap), DNS management was switched to **Namecheap BasicDNS** to enable direct host record configuration.

| A Record | @ | 20.5.169.97 | Automatic |
| A Record | www | 20.5.169.97 | Automatic |

Four A records were created, all pointing to the same Azure VM IP. Nginx handles the routing to different content based on the subdomain — demonstrating a multi-purpose server architecture from a single IP address.

## 5. SSL/TLS Certificate Setup

### Why HTTPS Matters

HTTP transmits all data in plain text, allowing anyone on the network path to intercept communications. HTTPS uses TLS encryption to ensure data confidentiality and integrity between the browser and server. Modern browsers also mark HTTP sites as "Not Secure", deterring visitors.

### Certbot Installation

```bash
sudo apt install -y certbot python3-certbot-nginx
```

### Certificate Issuance

Initial certificate covering the root and www subdomains:

```bash
sudo certbot --nginx -d alazimazxyz.xyz -d www.alazimazxyz.xyz
```

Later expanded to include the status subdomain:

```bash
sudo certbot --nginx -d alazimazxyz.xyz -d www.alazimazxyz.xyz -d status.alazimazxyz.xyz --expand
```

### Domain Verification (HTTP-01 Challenge)

Let's Encrypt verifies domain ownership using the **HTTP-01 challenge**: a verification token is placed at a specific URL, which the Let's Encrypt server then accesses to confirm control over the domain. This challenge succeeded because DNS was properly configured to point to the server.

### Automatic Renewal

Certbot installs a systemd timer that checks twice daily for certificates expiring within 30 days and renews them automatically:

```bash
sudo systemctl status certbot.timer
```

This "set it and forget it" approach prevents the common production failure where certificates expire because someone forgot to renew them.

## 6. Custom Security Audit Script

### Purpose

A custom Bash script was developed to perform automated security health checks on the server and publish the results as a styled HTML dashboard accessible at [https://status.alazimazxyz.xyz](https://status.alazimazxyz.xyz).

Unlike a typical lab activity script that prints text to the terminal, this script demonstrates real-world DevOps practice: **continuous monitoring with a publicly accessible, professionally styled dashboard that updates automatically**.

### Why This Script Is Creative and Useful

| Lab activity baseline | This script's contributions |
|---|---|
| Prints text to terminal only | Generates styled HTML dashboard with cards |
| Run manually when needed | Runs automatically every hour via cron |
| Output disappears when terminal closes | Output is persistent, public, and verifiable online |
| One or two basic checks | Seven distinct security checks |
| Local-only utility | Published live at a real public URL |
| No state interpretation | Calculates derived values (e.g. SSL days remaining) |
| Static structure | Color-coded status badges based on logic |

This is **not a modified lab activity** — it is an original creation built specifically to address a real-world server operations problem: continuous, automated security visibility.

### Seven Security Checks Performed

| # | Check | Linux Tool Used | What It Detects |
|---|---|---|---|
| 1 | Failed SSH login attempts (24h) | `journalctl` + `grep` | Brute-force attack attempts |
| 2 | Active SSH sessions | `who` + `wc -l` | Unauthorized concurrent access |
| 3 | Listening TCP/UDP ports | `sudo ss -tuln` + `awk` | Unexpected exposed services |
| 4 | UFW firewall status & rules | `sudo ufw status` | Misconfigured/disabled firewall |
| 5 | SSL/TLS certificate expiry | `openssl s_client` + `x509` | Certificates near expiry |
| 6 | Pending system updates | `apt list --upgradable` | Unpatched vulnerabilities |
| 7 | System resource health | `df`, `free`, `uptime`, `uname` | Disk, memory, load, kernel |

### Script Documentation (Inline Comments)

The script is **fully documented inline**. Anyone reading the source can understand its purpose without external context. Documentation appears in three forms:

**1. File header block** — explains the script's purpose, author, project, and full list of checks:

```bash
#!/bin/bash
# Security Audit Dashboard Generator
# Project : ICT171 Cloud Server Project
# Author  : MD Abdullah Al Azim (36018444)
# Murdoch University - 2026 S1
#
# Purpose:
#   Performs automated security health checks on the server and generates
#   a polished HTML dashboard published at https://status.alazimazxyz.xyz
```

**2. Section comments** — every functional block has a comment explaining its role:

```bash
# Data Collection Section

# (1) Failed SSH login attempts from system journal (last 24h)
FAILED_SSH=$(sudo journalctl _COMM=sshd --since "24 hours ago" 2>/dev/null | grep -ci "failed password" || echo "0")
```

**3. Logic-step comments** — non-obvious calculations are explained:

```bash
# Compute SSL certificate days remaining
if [ -n "$SSL_RAW" ]; then
    SSL_EXPIRY_EPOCH=$(date -d "$SSL_RAW" +%s 2>/dev/null)
    NOW_EPOCH=$(date +%s)
    SSL_DAYS_LEFT=$(( (SSL_EXPIRY_EPOCH - NOW_EPOCH) / 86400 ))
fi
```

A new reader can follow the entire script top-to-bottom and understand both **what is happening** and **why each step is necessary**.

### Verifiable Output (Live Dashboard)

The script's output is **published online and is independently verifiable by anyone**, including markers, without needing access to the server.

🔗 **Live dashboard:** [https://status.alazimazxyz.xyz](https://status.alazimazxyz.xyz)

The dashboard:

- Displays a **"Last updated" timestamp** at the top that changes every time the script runs
- Shows all seven security checks as separate visual cards
- Uses **color-coded status badges** calculated from the data
- Is **automatically refreshed every hour** by the cron job — no human intervention required

This means the dashboard is not a static screenshot or pre-rendered HTML — it is the **genuine, current output** of a Bash script running on this server. The timestamp at the top of the page is the clearest proof of this; running the script via SSH and refreshing the dashboard will show a matching, updated timestamp.

### Deployment Steps

```bash
# 1. Create the scripts directory
mkdir -p ~/scripts

# 2. Download the script from this repository
curl -o ~/scripts/security-audit.sh https://raw.githubusercontent.com/al-azim-az/ict171-cloud-server-project/main/security-audit.sh

# 3. Make it executable
chmod +x ~/scripts/security-audit.sh

# 4. Create the output directory served by Nginx
sudo mkdir -p /var/www/status

# 5. Run it once to generate the initial dashboard
sudo bash ~/scripts/security-audit.sh

# 6. Schedule it to run every hour via cron
(sudo crontab -l 2>/dev/null; echo "0 * * * * /bin/bash /home/azureuser/scripts/security-audit.sh >> /var/log/security-audit.log 2>&1") | sudo crontab -
```

### Nginx Configuration for the Status Subdomain

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name status.alazimazxyz.xyz;

    root /var/www/status;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }

    # SSL configuration added by Certbot during certificate expansion
}
```

The five-field cron expression `0 * * * *` translates to "at minute zero of every hour, every day, every month, every weekday". This ensures the dashboard data is never more than an hour stale.
